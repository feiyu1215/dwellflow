# 装修同步 · 空间巡场模块（重新设计）

> 2026-10-02
> 起因：原「工序索引」方向性错误——颗粒度做到施工工序（水电/防水/泥瓦…），超出产品能力范围且实现成本过高。
> 本文回答四件事：**改了算什么、模块是什么、边界在哪、哪里还没想清楚。**

---

## 0. 方向性修正：确认移除什么

| | 原设计（工序索引 / 7×6 矩阵） | 新设计（空间巡场） |
|---|---|---|
| **索引维度** | 工序（水电→防水→泥瓦→木工→油漆→安装→软装，7 行） | **空间**（客厅 / 主卧 / 厨房 / 卫生间 …） |
| **承载内容** | 装修施工环节 | **我在哪** |
| **颗粒度** | 细到具体施工工序 | **只到房间** |
| **与图的关系** | 图是展示工序的配图 | **索引项与背景场景图一一对应** |
| **切换方式** | 左右滑切模块 / 上下滑切工序 | **切换空间，视角展开浏览** |

**整体移除**：
- ❌ 7 个工序行（水电 / 防水 / 泥瓦 / 木工 / 油漆 / 安装 / 软装）
- ❌ 7×6 的矩阵结构（那个 6 列横轴一并废掉）
- ❌ 上下滑切工序的手势用途（见第 5 节，需重新安排）

**保留**：
- ✅ 左右滑动切换的手势（改为切换空间）
- ✅ 状态可视化（改为按空间聚合）
- ✅ 悬浮 AI 助手

## 1. 这个模块是什么（一句话）

> **用户在这套房子里"走"。每到一个空间，看到这个空间的场景，以及这里查得怎么样了。**

它不是一个"功能列表"，是一个**位置**。用户打开它，第一反应应该是"哦，我在客厅"，而不是"这里有 42 个格子"。

---

## 2. 为什么移除工序颗粒度（补充我的判断）

你给的理由是"超出产品能力范围 + 成本过高"。我补一层我的理解，因为这条会影响后面所有决策：

**这个产品不该教用户怎么施工，该帮用户记住"哪里还没看"。**

工序细分（水电要查几个点位、防水要做几遍）等于把**施工规范和排期责任**扛到自己身上——那是施工队和监理的活。一旦做到那个颗粒度：
- 内容维护成本 → 无底洞（不同地区工艺标准不同、不同房子做法不同）
- 责任风险 → 我们说"防水该做两遍"，出了事算谁的
- 用户负担 → 工地上最忙的人被要求先选分类

**砍掉之后，产品边界立刻清晰了：我们只负责"位置 + 状态"，不负责"工艺"。**

## 3. 功能逻辑（新）

### 3.1 三个组成部分

```
┌──────────────────────────────┐
│  ①  当前空间（全屏场景）        │
│      —— 我在这里                │
│      —— 叠加这间房的状态         │
│                              │
├──────────────────────────────┤
│  ②  空间索引条（底部）          │
│      客厅 | 主卧 | 厨房 | …     │
│      —— 与场景一一对应          │
│      —— 我还能去哪              │
└──────────────────────────────┘
```

### 3.2 数据模型（索引项 ↔ 场景 一一对应）

```js
Space = {
  id:     'living',        // 唯一键，索引项与场景共用
  name:   '客厅',           // 索引条上显示
  scene:  <场景图>,         // 一一对应：切到哪个 id，就显示哪张 scene
  scope:  { done: 12, total: 16 },   // 状态同步：查了多少
  flaws:  1,                // 状态同步：发现几处问题
  peers:  ['bed1','kitchen'] // 相邻空间，决定左右滑去哪
}
```

**"一一对应"的硬约束**：索引项的 id 就是场景的 id。没有"有索引没场景"或"有场景没索引"的项——**这个模块里，空间列表 = 场景列表，同一个数组**。

### 3.3 交互

| 动作 | 结果 |
|---|---|
| **点索引项** | 切到该空间，背景场景交叉淡入，状态条同步更新 |
| **左右滑** | 切到**相邻空间**（由 `peers` 决定，不是简单的前一个/后一个） |
| **停下** | 该空间状态浮现（进度 + 缺陷数） |
| **进下一步** | 点场景中的某处 / 或点"查看这间" → 进入节点层（本模块之外） |

### 3.4 状态同步同步什么

三种可能，需要拍板（见第 5 节第 7 条）：
- A. 只同步**进度**（已查 / 总数）
- B. 只同步**问题**（这间有几处缺陷）
- C. 两者都同步（推荐：进度给安全感，问题给紧迫感）

## 4. 定位与边界

### 它负责
| 职责 | 说人话 |
|---|---|
| 回答**"我在哪"** | 当前是哪个空间 |
| 回答**"这里怎么样"** | 这间查了多少、有没有问题 |
| 回答**"我还能去哪"** | 空间列表 + 相邻关系 |

### 它不负责
| 不负责 | 该谁负责 |
|---|---|
| 具体施工工序（水电/防水/泥瓦…） | **已移除**。那是施工队和监理的活 |
| 单个检查项的判定（这个点位合不合格） | 下一层：**节点层**（点进某个具体位置） |
| 施工进度与排期 | 不是这个产品的活 |
| 现场照片的产生 | **UGC**——用户自己拍，本模块只负责显示 |

### 一句话边界
> **本模块只管"空间"和"状态"两件事。任何需要判断"工艺对不对"的内容，都归下一层。**

## 5. 当前设计里还没想清楚的部分（需要你拍板）

这 7 条是我梳理时发现真正模糊的地方，**不拍板就没法往下做**：

### ① 上下手势放哪？
原来"上下滑切工序"。工序移除后，上下滑干什么？
- A. 取消（只保留左右切空间）
- B. 给"查看方式"（如 平面 / 环视）
- C. 给"层"（吊顶 / 墙面 / 地面）——⚠️ 但这可能又变成细分工序，要小心

**我的倾向**：A，先取消。不确定用途就留着不动，比硬塞一个用途好。

### ② 场景图从哪来？——**最大的一条**
- 我们画的（示意图）？还是用户拍的照片（UGC）？
- **关键盲点：用户还没拍照时，这个空间显示什么？** 一个三室一厅，用户刚装修时只有毛坯，6 间房可能一张照片都没有。那时候巡场界面是空的——这是必须解决的。
- 备选：没照片时显示**我们预置的线稿房间**（就是图层那套手绘），有照片后替换

### ③ 相邻关系谁定义？
客厅的"左边"是主卧——这是物理事实。但：
- 我们预置？（那每套户型都要预置一遍）
- 用户自己标？（增加负担）
- 不定义相邻，左右滑就只是**上一个/下一个**列表项？

**我的倾向**：先不做真相邻关系，左右滑 = 切换列表项。等户型做得多了再考虑。

### ④ 切换是"跳"还是"走"？
- **跳**：交叉淡入淡出，快，像翻页
- **走**：带方向位移，像挪动脚步，慢但更有"在场感"

**我的倾向**：跳为主。因为用户在工地上，手上可能在忙，快比沉浸重要。

### ⑤ 户型不同，空间数量不同，索引条怎么自适应？
一室一厅 4 个空间，三室一厅 6 个，复式可能 8+ 个。索引条横排会溢出。是横向滚动，还是两行？

### ⑥ "展开浏览"要做到什么程度？
你说的是"周围空间视角的展开浏览"。这里有两种理解：
- **浅**：切换空间时，场景图有轻微视差，感觉视野在展开
- **深**：真允许在场景内左右环视（转视角），像站在房间里转头

深的那版成本高得多。**需要明确要哪个。**

### ⑦ 状态同步的粒度？
见 3.4。只同步进度？只同步问题？还是都要？

---

## 6. 我建议的下一步

1. **先拍板第 5 节的 7 条**（尤其 ② 场景图从哪来、⑥ 展开到什么程度）——这两条决定了原型长什么样。
2. 拍板后我做**可交互原型**，用预置线稿场景跑通"切换 + 状态同步"，验证手感。
3. 再回头定：这套场景图是预置线稿，还是等 UGC 填充。

| 我之前的做法 | 错在哪 | 现在 |
|---|---|---|
| 围绕 7×6 工序矩阵做设计 | **颗粒度超纲**：把施工规范的活扛到自己身上 | 索引维度改为**空间**，只到房间 |
