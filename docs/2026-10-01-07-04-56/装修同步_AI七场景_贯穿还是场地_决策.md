# 七个 AI 场景：贯穿还是场地？——五重审视后的决策

> 2026-10-02 · 深度思考（重档 · 全面思考）
> 问题来源：大将军直觉"七个流程可以贯穿始终，比如我在看某个房间时也能用；但有些也可以有自己的场景——该怎么搞？"

---

## 第一重审视：问题与领域

- **表层请求**：七个 AI 流程，各配一块场地，还是贯穿所有场景？
- **深层目标**：用户在**任何时刻、任何地方**都能用上对的那类 AI 帮助，同时**入口不泛滥、可理解、范围不出错**。
- **关键问题（可验证）**：
  - Q1：七类任务里，哪些**强绑定对象**（必须先选中某批次/某问题才能用），哪些**弱绑定**（一张照片、一段聊天就能发起）？
  - Q2：入口重复的代价 vs 入口远离使用时刻的代价，哪个更大？
  - Q3：贯穿式会不会重蹈 K04（假万能输入框）？
- **代价**：判断错 → 要么入口泛滥（万能按钮到处跑、范围装配出错），要么入口太深（在房间里想看图，得先跑回料场）。
- **领域**：信息架构（对象导向 vs 任务导向导航）+ AI 产品交互。
- **这一重改变了什么**：问题从"每块场地配不配 AI"改写为"**每个任务的发起、选对象、产物落点，各应该跟谁走**"——原来问的是地方，其实要拆的是任务的三个阶段。

## 第二重审视：理论体系与判断主轴

- **Norman（知识在外部世界）**：工具应出现在使用它的地方 → 支持"就地"。
- **对象导向信息架构**（Gmail 式：操作跟着对象走）：本产品是重对象产品（批次/问题/记录/约定都是对象）→ 对象导向优先于任务导向。
- **Nielsen 可发现性**：能力全藏进对象，用户不知道"AI 能干什么" → 需要一个稳定的可发现入口。
- **关键矛盾**：入口跟着对象走（就地可用）**vs** 入口可发现可预期（知道 AI 能干啥）。
- **判断主轴**：**按"任务的对象依赖度"分层，而不是按场地一刀切。**
- **这一重改变了什么**：排除了"七个场地各配一个 AI 按钮"和"一个万能 AI 跟人走"两个极端——真正的变量是任务的绑定强度。

## 第三重审视：关键事实与综合体系

关键事实：

1. **PRD 自己写的是"默认入口"**（§7 表头原文），且 M8D-1 批次明确叫"记录整理+图片观察**就地**入口"——PRD 已承认两种形态并存。（事实）
2. **K04 已确认**：假万能输入框是踩过的坑——万能入口 = 万能困惑。（事实）
3. **逐任务对象依赖分析**（推测，依据 PRD §7 的输入定义）：

| 任务 | 对象绑定 | 归层 |
|---|---|---|
| 材料核对 | **强**（材料+批次+批准基线） | 场地内（料场） |
| 整改辅助 | **强**（目标问题） | 场地内（告示板） |
| 预算资源 | 中（需求+库存+口径） | 固定页（账台） |
| 总结交接 | 弱（项目级范围） | 固定页（概览） |
| 记录整理 | 半（选中一条记录） | 就地（房间便签） |
| 图片观察 | **弱**（任意照片） | **贯穿发起** |
| 咨询整理 | **弱**（外部聊天记录，无场地归属） | **贯穿发起**，产物去图纸桌 |

4. **用户直觉校准**："我看某个房间时也能用这些"——在房间里想用的，恰好是图片观察和记录整理。直觉与依赖分析吻合。（推测，方向与事实3一致）

**综合理论体系（本问题的解释模型）**：

> **每个 AI 任务拆三段：发起（可贯穿，跟人走）→ 选对象（永远就地，跟对象走）→ 产物（永远有固定落点，跟产物走）。**
> "贯穿"的真正含义不是七个按钮跟着人跑，而是：**发起无门槛、对象就地选、产物有归处。**

- **这一重改变了什么**：把"场地 vs 贯穿"的二元对立拆掉了——大部分任务天然是"就地选对象"，真正可贯穿的只有弱绑定任务。

## 第四重审视：反方压力与前提辩证

- **方案 A（场地独占）**：七任务只在各自场地可用。
  反方（用户已给）：在房间里想拍张照让 AI 看，得先跑回对应场地——**违背使用时刻**。A 被击破。
- **方案 B（全贯穿万能入口）**：一个 AI 按钮到处可发起七任务。
  **最强反方**：这就是 K04 假输入框复辟——万能入口下用户面对七个任务不知选哪个；更致命的是**跨场地选对象 = 范围装配混乱**（K01/K02 的教训：材料不属于房间，在房间里发起材料核对，范围算谁的？）。B 被真实击破。
- **方案 C（三层模型，主推）**：发起贯穿 / 对象就地 / 产物归位。
  **对 C 的最强反方**：在房间里发起材料核对这种跨场地任务怎么办？
  前提辩证：这个场景真实存在吗？在房间里想核材料，多半是"看到这间房的材料有问题"——那本质是**图片观察**（拍下来→待确认问题→流转到料场/告示板）。**高频跨场地需求已被"图片观察→问题流转"覆盖**，C 不需要跨场地选对象，只需要产物流转。
  判断动作：**C 成立，边界收缩——贯穿发起只覆盖弱绑定任务（图片观察、咨询整理、记录整理的发起）；强绑定任务（材料核对、整改辅助）保持场地内入口，不做贯穿。**

前提补证动作：原型验证时观察用户在房间场景点 AI 后的意图分布；M8D-1 本来就是"就地入口"批次，验证顺路，不加成本。

- **这一重改变了什么**：C 赢了，但被反方削掉了一半——"贯穿"从"七个都能"收缩为"三个弱绑定的发起能贯穿"。

## 第五重审视：全貌收束与可验证

### 最终架构：AI 能力三层，场地承载对象与产物

| 层 | 跟谁走 | 内容 |
|---|---|---|
| **贯穿发起** | 跟人走 | 图片观察（任何场地可拍照发起）、咨询整理（任何场地可粘贴发起）、记录整理（从便签发起） |
| **就地入口** | 跟对象走 | 材料核对（料场批次旁）、整改辅助（告示板问题旁）、记录整理（房间便签） |
| **固定落点** | 跟产物走 | 核对记录→料场；待确认问题→告示板；咨询草稿→图纸桌；估算→账台；报告→概览 |

### 落到 UI 的形态（防 K04 复酒的硬规矩）

- 贯穿发起的 AI 呼吸点：点开是 **2～3 个诚实任务卡**（拍照看看 / 整理讨论 / 记一笔），**不是聊天框**；
- 就地入口：场地内对象旁的小标记（批次旁"核对"、问题旁"拟预案"、便签旁"整理"）；
- 每个入口点开后第一屏 = **资料范围预览**（AI 将看到什么），可审可改——K03 的教训直接变成设计。

### 场地数量不变

料场、告示板、图纸桌、监控屏四块场地 + 房子/账台/概览普通页——**场地承载"对象和产物"，AI 能力部分贯穿**。大将军的两句直觉（"可贯穿始终"+"也可有自己的场景"）都对，分层后同时成立。

### 验证与转向

- **成功信号**：房间场景里用户点 AI 后主要发起拍照/整理（意图分布符合预期）；料场就地核对的完成率 ≥ 贯穿发起的。
- **失败信号 / 转向条件**：如果用户在房间里频繁试图发起材料核对——说明"产物流转"不够顺（拍照→问题→料场这条路断了），该修的是流转，**不是**把材料核对做成贯穿入口。
- **不解决什么**：3D、自由输入聊天框（另批）、跨项目任务、自动销案。

---

**最终判断**：采用方案 C 三层模型——"**发起贯穿、对象就地、产物归位**"。贯穿的只有图片观察、咨询整理（发起侧）和记录整理（便签侧）；材料核对、整改辅助留在场地内；产物各有归处。场地数量不变，AI 能力贯穿。
结论可信度：**较高**——与 PRD"默认入口"措辞兼容、与 K01/K02/K03/K04 缺陷教训一致、与用户直觉吻合；主要不确定项（房间场景的 AI 意图分布）已带补证动作且零额外成本。

## 终版修正（大将军，同日）：AI 代办 + 落点跳转

### 大将军原话要点
> "你想在那个东西做这东西，那你就是直接和 AI 交互即可呀。**是让 AI 去做，你不去做**。我们的 AI 除了提供分析能力，还是提供**帮忙记录的能力**。他可以在看这里的时候就能去做那东西，同时也可以**快速跳转到他想要的地点**，这样就解决了。"

### 这一修正解决了什么

方案 C 剩下的硬骨头是"**跨场地选对象**"——人得自己走到对象跟前才能选它。
解法：**选对象这一步也不归人，归 AI。** 人永远不导航；人只做两件事：**表达 + 拍板**。

### 终版交互循环（升级方案 C 的五步）

> **人表达 → AI 定位 → AI 代办（起草/预填）→ 就地拍板 → 落点跳转**

1. **人表达**：任何场地唤起 AI——说话、拍张照、贴段聊天记录（"这批瓷砖和订的对不上啊"）；
2. **AI 定位**：从表达 + 当前上下文识别意图和对象（"这是料场里待核对的瓷砖批次 #3？"）——给候选 + 置信度，**一键改判**（正是《延迟定型与自主度契约》的 provisional type 机制，正好咬合）；
3. **AI 代办**：AI 跑腿——起草核对差异、整理条目、拟预案、预填表单。**跑腿 = 定位 + 起草 + 预填 + 跳转，不含拍板**；
4. **就地拍板**：AI 把人**跳转**到该对象的就地确认页（料场的批次、告示板的问题）——确认界面就是对象所在处，完整资料范围天然可见（K03 的范围预览自动满足）；
5. **落点跳转**：确认后告知"产物已写入哪里"，带跳转链接——**motion carries state：跳转本身就是状态的呈现**。

### 和 PRD 红线的关系（一条不破）

| PRD 红线 | 终版模型怎么守 |
|---|---|
| AI 不自动批准/写库 | "让 AI 去做" = 让 AI **跑腿**（定位/起草/预填/跳转），**拍板永远在人** |
| 资料范围预览（K03） | 拍板发生在对象的就地确认页——范围就是该页面资料本身 |
| 诚实入口（K04） | 唤起 AI 后是**意图识别 + 候选确认**，不是假装万能的聊天框；听不懂就明说，给候选让人改 |
| 归属不漂移（K02） | AI 定位对象时给归属候选（全项目/某工序/待补），人改判后按改判走 |

### 场地系统的最终身份

- **场地 = 物件的住址**（对象住哪、产物落在哪），负责"可找到、可巡"；
- **AI = 跑腿员**（定位、代办、跳转），负责"不用找"；
- **穿门/左右滑** = 主动游览方式，保留。
- 三者各司其职：**逛（场地）、办（AI）、拍板（人）**。

### 验证信号（更新）

- 成功：用户完成"拍照 → AI 定位候选 → 确认 → 落点查看"全链路材料核对，中途**没有手动导航**；
- 失败/转向：AI 定位候选被改判率 >50% → 修上下文装配；用户无视跳转链接手动找产物 → 落点提示不够醒目。

## 辨析：这算不算"小程序 CLI 化"？（大将军追问）

**对了一半。** 这个直觉指向的正确名字是"**委派式交互（intent-driven）**"，不是 CLI。

| | 真 CLI | 我们的 AI 代办 |
|---|---|---|
| 表达 | 精确命令语法 | 自然语言/照片/粘贴 |
| 执行 | 回车即执行 | **回车 = 起草，拍板才执行** |
| 出错 | 语法报错，人重试 | AI 给候选 + 置信度，人改判 |
| 输出 | 文本结果 | 结果卡：做了什么 + 对象是谁 + 范围是什么 + 产物在哪（跳转链接） |

**采纳 CLI 的三个优点**：语言表达意图（不找入口）、输出可预期（结构化结果卡）、结果带落点。
**拒绝 CLI 的两个缺点**：语法负担（AI 兜住模糊表达）、即时执行（PRD 红线：AI 不自动批准/写库）。

一句话：**CLI 是执行接口，我们是委派接口——回车即执行 vs 回车即起草、拍板才执行。**
参照物不是终端，是 Raycast / Spotlight / slash-command 的"命令面板"模式，底层结构对应 ag-ui 的 tool-call + 结果事件。

## 定论（回应"应不应该 CLI 化"）：应该

上一轮"对了一半"说的是**形态**，没有把"该不该"说清楚。明确如下：

**应该 CLI 化——按"内核"意义，不按"外壳"意义。**

三层拆开：

| 层 | 判断 | 理由 |
|---|---|---|
| **外壳（终端、命令语法）** | ❌ 不要 | 小程序没有终端；用户不该背语法 |
| **内核（能力命令化）** | ✅ **必须** | **委派的前提 = 能力能被一句话表达**。一条 AI 代办 = `动词 + 对象 + 范围 + 产物落点`。说不出这条结构的任务，AI 就没法代办——所以命令化不是可选项，是委派的地基 |
| **皮肤（表达方式）** | ✅ 多样 | 自然语言 / 任务卡 / 语音 / 拍照——同一执行内核，多个入口皮肤 |

**落地到工程**：`core/ai-contract.ts`（510 行 AI 契约与校验模块）已经是命令内核的雏形——每个任务有专用输出契约。"CLI 化" = 在它之上加一个**统一表达入口**：把七个任务当七条命令，每条命令的执行留痕对应 PRD 已有的幂等与审计要求。

一句话：**上一轮"拒绝 CLI"拒绝的是外壳和即时执行；这一轮"应该 CLI 化"说的是内核——能力命令化是委派的必要条件，两者不矛盾。**
