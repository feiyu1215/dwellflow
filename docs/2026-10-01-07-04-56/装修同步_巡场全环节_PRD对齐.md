## 2. 巡场 = 场地系统：三种场地

| 场地 | 走动方式 | 场景样态（同一手稿亮底视觉语言） | 里边的 AI 入口（PRD §7 默认入口） |
|---|---|---|---|
| **房子**（空间） | 穿门走动（v3 已做） | 客厅/厨房/卫生间……每间一张场景图 | 图片观察、记录整理（就地） |
| **路**（工序） | 沿路推进 | 7 工序的路，节点在路上 | 各阶段节点的任务 |
| **事务地块**（模块） | 进场办事 | **料场**（材料堆/到货批次/缺口清单）、问题板、账台、证据墙 | **材料核对**→料场；**整改辅助**→问题板；**预算资源**→账台；**总结交接**→项目概览 |

**材料准备的直接回答：给它一块"料场"场地。**
材料核对 AI 的默认入口本来就是材料模块（PRD §7），料场场景 = 到货堆 + 待核对批次 + 批准基线对照 + 缺口清单。它不是某个房间，也不完全属于某道工序——这正是下一条红线的原因。

## 3. PRD 给巡场划的四条红线（踩了就是重蹈 K 系列缺陷）

1. **范围一致（K01 / R-N02）**
   场景热点必须携带真实范围 `(stageId, moduleId, roomId)`。"点客厅的材料"只显示客厅的材料——**不许拿全项目数据冒充当前场景**。这正是 K01 缺陷（只传 route 不传筛选）的教训。

2. **三个数据范围（R-N05 / K02）**
   材料可以属于：**全项目**（如全屋合同）/ **某道工序** / **归属待补**（旧数据）。料场场景必须三分区呈现，**禁止把缺归属的材料自动塞进当前工序**（K02 缺陷）。

3. **完工语义（K06）——"进度上色"要改口径**
   PRD 明确：**阶段顺序 ≠ 完工**，更早阶段只能叫"此前阶段"，不可宣称"已完成/已验收"。
   所以"全彩 = 完工"这个说法**不合格**。正确口径：
   > **上色程度 = 该空间的"已记录内容覆盖度"，事实来源是节点计数——不是验收状态。**
   全彩的意思是"这里记录得很全"，不是"这里验收过了"。文案、图例都要按这个改。

4. **诚实入口（K04 / R-N03）**
   助手入口不能是假输入框——**v2/v3 原型里的对话卡就是 K04 批判的那种假控件**，只是示意。真实版按 PRD §7 流程：明确任务 → 选择对象 → **预览资料范围** → 提交 → 复核 → 写回。真实自由输入是独立功能，等做的时候用 TDesign AI Chat 组件（ChatSender/ChatRecord/Attachments，小程序 MIT，清单已核验）。

## 4. 和开发节奏的关系（诚实排期，不插队）

PRD 的顺序是：**M8B-3A 缺陷收口 → 3B 归属模型 → M8C 助手上下文 → M8D 七类迁移 → M8E 空间进度（门控：稳定空间映射 + 业务状态）**。

- 巡场的整套设计 = **M8E 的设计前置 + 素材规格**，不插队；
- 但注意：**3B 的"归属模型"（scopeKind/stageId）恰好就是巡场热点需要的数据底座**——3B 做完，巡场的数据就通了；
- PRD 明确"不新增 3D"——我们的二维手稿路线与 PRD 无冲突；
- 现有产品里已有"空间/证据/监管视图（房间计数→相关内容）"——巡场是它的**升级**，不是外来物种。
